# Cloud save backups — #36 (Draft PR #116)

The local IndexedDB autosave remains the primary offline save. The Library offers opt-in backup/list for a verified, activated account and published playable games. No restore, conflict resolution, automatic sync or local overwrite in this slice.

## Design: private objects and metadata-only SQL

Migration 008 holds **metadata only**: verified account, game UUID, pinned hardware/save schema, digest, bytes, private storage key and pending/ready state. No save content is stored in PostgreSQL. Next.js Node server uploads private bytes to the dedicated private Neon bucket (`slopboy-cloud-backups-prod` for the canonical experimental Production deployment; `slopboy-cloud-backups-dev` for historical dev tests) under `backups/<account>/<game>/<backup>/<digest>.json`. The server checks the exact key/owner/game/digest contract; storage credentials stay server-only.

Neon credentials support branch-wide `storage:write`, **not** provider-enforced object-key prefix permissions. Owner explicitly approved this trade-off for a dedicated private dev bucket with application-enforced prefix. Never hand S3 credentials to the browser, or expose a presigned object URL without a fresh authorization check.

## Upload protocol

1. Verify identity/profile, Origin, UUID, playable eligibility, payload encoding and size.
2. Reserve a pending metadata row transactionally under the account advisory lock. Enforce 256 KiB/backup, 5 revisions/game, 10 MiB/account including pending reservations, unique SHA-256 per account/game.
3. Conditional private S3 PUT with `If-None-Match: *`; read the object back and confirm exact bytes and SHA-256.
4. Confirm metadata only after readback. Return `stored` and HTTP 201 only after backend acknowledgment. A confirmed digest replay is HTTP 200.
5. If confirmation throws, retry confirmation once (idempotent) without repeating the upload. If it remains ambiguous, return unavailable without deleting the object or releasing its reservation. A committed confirmation may have lost its response; deleting bytes here would corrupt a ready backup. Failed or interrupted requests may leave pending metadata/orphan objects. Pending rows older than 15 minutes are released on the next reservation. An audited reconciliation job, with safe fencing against in-flight writes and quota-abuse safeguards, remains a broad-rollout gate.

**FAIL CLOSED:** both `CLOUD_SAVE_BACKUPS_ENABLED=1` and `CLOUD_SAVE_CONDITIONAL_PUT_VERIFIED=1` must be explicitly set, together with a verified private bucket and server-only `AWS_ENDPOINT_URL_S3`, `AWS_REGION`, `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY`. Do **not** set the verification flag until a live provider test proves first conditional PUT creates the object, second PUT to the same key fails (412), original bytes stay intact and unauthenticated GET is denied. Live provider evidence on 2026-11-24: [Vercel Sandbox presigned-request probe](https://github.com/MohamedXIV/slopboy/pull/116#issuecomment-7125901303) returned 200, 412, original GET 200, anonymous GET 403; probe removed. The separate header-signed app adapter and hosted account/browser behavior still require validation. CI is not proof of either.

## Pre-launch hosted QA restriction

The current acceptance slice is restricted to an authenticated, email-verified database profile with role `admin`, including the Library UI. Other roles cannot invoke the feature. `CLOUD_SAVE_EXPECTED_TARGET` is non-secret JSON containing databaseHost, databaseRole, databaseName, authUrl, storageEndpoint, region and bucket. All actual environment URLs and the restricted database username must match this reviewed binding before the feature becomes available. This check compares configured targets, not credentials or connectivity. No environment URLs or credentials are returned to browsers. Keep the two feature gates off until deployment and provider evidence are reviewed; broader access waits for orphan reconciliation, abuse protections and hosted authorization acceptance. Only the ordinary authenticated API performs live signed uploads; no external credential probe.

## Production readiness diagnostics

When the feature is enabled but configuration fails the binding, the server logs a fixed readiness category such as `database_role_mismatch`, `auth_target_mismatch` or `storage_target_mismatch` at most once per warm process. These logs contain no connection values, credentials, account identifiers or save payload. Anonymous responses remain generic, and the guard still fails closed. Correct the indicated configuration directly in the Vercel dashboard and redeploy; never relax the role/branch binding or retrieve secrets into a debugging tool. A successful readiness check is configuration evidence only; live authenticated upload/readback still needs acceptance.

## Named snapshot transfer foundation (ADR-006)

The new `slopboy-cloud-snapshot-v1` canonical UTF-8 envelope carries game/device identity, slot and snapshot UUID/name, kind, source revision, nullable release/time, schema, exact payload bytes and SHA-256. It excludes session tokens, account IDs and storage keys. The existing 256 KiB object quota includes metadata/JSON expansion; oversized exports fail without altering local state. Future server endpoints must validate the exact canonical envelope and its inner digest before reserving the SHA-256 of the entire object. Legacy raw bytes remain distinctly typed in future metadata; do not guess a format from payload text. Rename changes envelope metadata and therefore the outer digest, not gameplay digest. Explicit keep-both restore creates independent local IDs and never activates or replaces a slot; incompatible/unknown provenance remains visible but cannot be opened. Compare by IDs and content, not timestamps; no automatic conflict winner. The new bounded server-only download helper requires exact authorized ready-row key, size and digest. It is used for existing upload readback; it is NOT a public restore endpoint. Next slice: additive metadata migration, owner-authorized lookup/list/reserve, distinct named/legacy quotas and routing without double-counting, reconciliation, UI and hosted QA. No migration or named cloud write is enabled by this foundation.

## Migration 009 — named metadata foundation

Add a separate metadata-only named snapshot table with restricted admin-QA list/reserve/confirm/ready lookup functions. The existing legacy table and objects are untouched. Each lane retains a five-object per-game cap; both share the original 10 MiB account byte cap and advisory lock, including pending rows. The 256 KiB cap covers the canonical envelope. List results never include private object keys; only the authorized server lookup returns a key. Pending named reservations are retained rather than expired/deleted until reconciliation is designed; a failed upload can consume quota, intentionally fail-closed. Rollback is blocked if any named metadata exists; disable rollout rather than drop retained records. New functions have PUBLIC execute revoked and require separately reviewed restricted web grants. No hosted migration, grants, API, or cloud feature activation in this slice. The future API must enforce reviewed per-game save capabilities, derive metadata from the validated envelope, bind the verified server subject, and check exact object bytes/digest before confirmation or restore.
