# Transactional protected cloud management (prelaunch foundation)

Migration 016 adds an optional SQL payload lane in the existing named metadata table. Existing object-backed records and their APIs are unchanged. Only the new SQL functions can delete or replace a transactional copy, requiring its exact backup UUID and full envelope digest. Replacement validates the new payload, subtracts the exact target's bytes from projected quota, tombstones the source snapshot identity, removes the old payload and inserts the new one in a single transaction. A rejected replacement preserves the old copy. Deleted snapshots cannot be resurrected through these new functions, including after a local rename. Delete replay is idempotent. New backups with a distinct snapshot ID remain possible. Legacy object rows are not eligible for deletion or replacement by these functions.

Shared account cap stays 10 MiB and five named copies per game. New named SQL lane has its own 16 MiB/1000 row global ceiling plus 1000 tombstones per account / 10000 globally; these are chosen QA ceilings, not a provider entitlement. Actual storage overhead needs measurement. All functions remain owner-only; no live changes or storage deletes. Rollback refuses retained SQL payloads or deletion history.

Before enabling: route new named writes through the atomic function (old reserve/confirm must not remain available to active writers), use exact readback with legacy object fallback, expose suppressed IDs to pinned worker and settle rejected pending intent without marking it uploaded, add explicit confirm-delete/replace UI and hosted tests. Existing named API remains unchanged until that transition. Inventory separates named SQL payloads from object storage.
